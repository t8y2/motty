A remote-desktop host opens as a tab that shows a picture instead of a terminal.

## Supported

- RFB 3.3, 3.7 and 3.8, including negotiation from RealVNC's 5.0 banner to 3.8
- Security types None, VNC Authentication, RealVNC RSA-AES and certificate-based VeNCrypt 0.2
- Encodings Raw, CopyRect, RRE, Hextile and ZRLE
- Desktop resize
- Pointer, keyboard and text clipboard

## RealVNC system accounts

A RealVNC server using **Always on** encryption and **UNIX password**
authentication can use RSA-AES. Enter its system username in the optional VNC
username field, or supply username and password when connecting.

The server-key dialog appears before credentials are requested. A saved identity
change stops the connection. Public fingerprints belong to the shared local
endpoint store: host entries with the same VNC address and port share trust, and
deleting a host preserves it. **Forget this server** removes the pin and the next
connection asks again. System-account passwords are stored separately from
traditional VNC passwords.

RA2 and RA256 encrypt the full VNC session with AES-128-EAX and AES-256-EAX.
RA2ne and RA256ne encrypt only authentication and require explicit permission
in the host editor. VeNCrypt supports X509None, X509Vnc and X509Plain over TLS
1.2 or newer; X509None encrypts the session without password authentication.

## Connect through SSH

<Callout type="warn">
  VNC Authentication is weak: DES with at most eight password characters and a
  challenge that crosses the network in the clear. The tab says "Not encrypted".
</Callout>

Use **Connect through SSH**. The host's address is then the SSH server. Motty uses
the saved SSH host with the same address and account (its port, algorithms and jump
route), or plain SSH on port 22, asks the SSH questions first, and opens
`127.0.0.1:<port>` from the SSH server through a `direct-tcpip` channel.

## In the tab

- Fit-to-window or 100% scaling; at 100% a larger picture pans with the pointer.
- While the picture has focus, Motty's shortcuts do not run and keys go to the
  remote. **Ctrl+Alt+G** releases the keyboard and takes it again.
- The status line shows the selected VNC security mode and its protection,
  separately from "Through SSH", plus size, scale, clipboard sharing and the escape chord.
- **VNC security details** shows authentication, cipher, negotiated TLS version,
  server fingerprint and the modes received during this handshake. VeNCrypt
  subtypes appear only when their offers were read. Details can be scrolled and
  copied, and are available from the toolbar, tab menu and command palette.
- A lost connection keeps the last picture, dimmed, with a Reconnect button.

## Clipboard

Per host, off by default, text only. RFB carries Latin-1, so other characters are
sent as `?`.

## Not supported

Anonymous VeNCrypt/TLS, Apple Remote Desktop authentication (macOS Screen Sharing needs
"VNC viewers may control screen with password"), Tight/JPEG, extended clipboard,
images in the clipboard, audio, file transfer, changing the remote resolution and
multiple screens. KasmVNC cannot be driven because it reads pointer events in a
non-standard format; TigerVNC and any server that follows RFC 6143 work.
Other RealVNC security schemes, including servers that offer only type 13, are
not supported by this RSA-AES implementation.

## What was verified

KasmVNC `Xvnc` on a Linux machine and TigerVNC in Docker, including through an SSH
tunnel. Physical keyboard and pointer interaction in a native window,
input-method composition, hidden or covered windows, macOS Screen Sharing and a
Windows VNC server still need manual testing.
An additional credential-free RealVNC Server 7.13.1.57 probe verified version
negotiation, its RSA-AES server proof, and system-account authentication selection.
Windows testing against a Raspberry Pi verified system-account login, desktop
display and clipboard sharing. Chinese text
still has the Latin-1 clipboard limitation. Reconnection and extended sessions
on that server still need manual testing.
