---
title: MCP server
description: Let external agents use your sessions through a local, token-protected server.
---
An optional MCP server exposes the same session tools to external agents such as
Claude Code.

It is **off by default**, listens on loopback only, and requires a bearer token.

## Enable it

In **Settings > MCP**, turn on **Allow external agents (MCP)**. The page
then shows the endpoint and the access token, with a button to copy the client
configuration. Resetting the token disconnects every client.

HTTP and the independent service each have their own client selection, preview
and copy button. Their client choices are saved separately. HTTP configuration
contains an endpoint and token; the independent configuration contains a program
to start and its `mcp-serve` argument.
The exported independent configuration also passes `--data-dir` so the child
uses the same authorized hosts and access settings as the current window.

<Callout type="warn">
  Anyone who has the HTTP token can use the access level chosen for the HTTP
  service. Keep it out of shared configuration.
</Callout>

### Access level

| Level | What a client can do |
| --- | --- |
| Observe | Read only. |
| Ask | Low-risk actions run automatically. Others need approval in Motty's AI panel; critical actions require typed confirmation. |
| Allow all | Run commands and read, change or delete files, including critical operations, without per-call approval. |

Choosing **Allow all** opens a risk confirmation. The option is saved and selected
only after confirmation; Cancel or Escape keeps the previous access level. It
applies to every client connected to the local MCP service and every session they
can access. Switching back to **Observe** or **Ask** restores that mode's limits
for new calls immediately.

## Tools

Full access keeps a red risk warning visible even while HTTP is disabled: the
saved level also applies when it is enabled again. Open windows synchronize the
shared HTTP access level. Full access explicitly skips cross-connection approval,
but preserves hard policy blocks and never expands the available sessions or
authorized saved hosts.

| Tool | Does |
| --- | --- |
| `list_sessions` | List open sessions. |
| `terminal_read` | Read a terminal's content. |
| `terminal_exec`, `terminal_exec_many` | Run commands in a terminal. |
| `terminal_start`, `terminal_poll`, `terminal_stop` | Start a long-running terminal command without waiting, read its new output by offset, and stop it (desktop HTTP MCP only). |
| `tool_output_read` | Page through retained desktop HTTP `terminal_exec` output without rerunning the command. |
| `sftp_list`, `sftp_read` | List and read remote files. |
| `sftp_write`, `sftp_remove` | Change remote files. |

In Observe mode only the read tools are available.

Desktop HTTP `terminal_exec` still returns a bounded head-and-tail preview (about
64 KiB). When a complete result was retained, its response includes an
`output_id`. Call `tool_output_read` with that ID, a UTF-8 byte `offset` starting
at 0, and optional `max_bytes` (4–65536). The `structuredContent` of the
execution result also contains `preview`, `output_id`, `exit_code`, `truncated`,
`total_bytes`, and `source_output_lost`. Read `data` and pass `next_offset` into
the next call until `eof` is true. Offsets inside a UTF-8 character or past the
end are rejected. This is normalized terminal text, not raw PTY bytes.

HTTP clients must send the `Mcp-Session-Id` returned by `initialize` with later
requests; another MCP session cannot read their results even with the same
HTTP token. The built-in `mcp-bridge` carries this header automatically.
Each result is limited to 4 MiB and ten minutes. The service caches at most
16 MiB, evicts old results when full, and clears them when HTTP MCP is stopped
or reconfigured. If the command output was irrecoverably lost (for example,
it exceeded the retention limit), the preview reports that explicitly instead
of offering an unusable ID. This feature applies only to desktop HTTP
`terminal_exec`, not standalone `mcp-serve` or `terminal_exec_many`.


### Long-running terminal jobs

For builds, installs and deployments that outlive one tool call, start the
command with `terminal_start`. It goes through the same risk assessment and
approval as `terminal_exec`, types the command into the visible terminal and
returns a `job_id` immediately. Then:

- `terminal_poll` takes the `job_id` and the previous `next_offset` and returns
  the new output. `state` is `running`, `completed` (with `exit_code`),
  `cancelled` (stopped by `terminal_stop`), `interrupted` (the user pressed
  Ctrl-C and took the terminal back) or `disconnected` (the shell ended before
  the command did). A line still being written is returned separately as
  `pending_line` and joins `data` once complete. Each job keeps its newest
  2–4 MiB of output; output dropped before it was read is reported in
  `skipped_bytes`.
- `terminal_stop` sends Ctrl-C and briefly waits for the shell prompt to come
  back. `interrupt_sent` says whether this call actually sent the interrupt
  (it sends nothing for a job that already finished). `terminal_ready`
  separates whether the next command can be typed: `ready` (the prompt was
  seen), `busy` (the command still runs or the prompt did not return),
  `unconfirmed` (the shell reports no prompt information) or `closed`.

A terminal runs one job (or one `terminal_exec`) at a time. A job belongs to the
MCP session that started it (`Mcp-Session-Id`); other sessions get "job not
found", and finished jobs stay readable for ten minutes. If the client
disconnects the command keeps running, but a new MCP session cannot recover the
job id; inspect the terminal or press Ctrl-C there. Motty never replays a
command.

## Clients that only speak stdio

`motty mcp-bridge` relays MCP over stdio to the running application:

```sh
MOTTY_MCP_TOKEN=<token> motty mcp-bridge --url http://127.0.0.1:<port>/mcp
```

The token goes in an environment variable because a flag would show in the process
list.

## Without the window

`motty mcp-serve` is an MCP server that needs neither the window nor a port. An
agent starts it as a child process when it needs it, and it ends with the agent;
Motty does not have to be open. In **Settings > MCP**, **Connect a client** copies
the entry for the client you chose.

```sh
claude mcp add motty-hosts -- /path/to/motty mcp-serve
```

It works on the saved hosts you opened to agents, over connections of its own. A
host is closed to agents until you turn on **Allow MCP agents to use this host**
under **Advanced** in its settings; the choice is kept on this computer only, so a
host that syncs in from another device starts closed.

| | |
| --- | --- |
| Tools | Depending on the access level: `list_sessions` (authorized saved hosts), `terminal_exec`, `terminal_exec_many`, `sftp_list`, `sftp_read`. Allow all also offers `sftp_write` and `sftp_remove`. There is no terminal screen to read. |
| Commands | Run through an SSH exec channel: no terminal, and nothing carries over from one call to the next. |
| Read only | The default. **Commands** lets agents run commands rated low risk. Anything that would need your approval is refused, because nobody is there to ask. |
| Allow all | Saved and selected only after risk confirmation. Runs commands of any risk level and writes or deletes files on authorized hosts without approval. Configured separately from HTTP; applies the next time the client starts the service. |
| Sign in | From what Motty saved: keys, ssh-agent, and passwords or key passphrases in the saved passwords. A master password locks those out; use a key. A server that asks for a one-time code cannot be used. |
| Host keys | Only keys Motty already trusts. An unknown or changed key is refused; connect to the host once from the window. The agent never trusts a key. |
| Activity | Settings > MCP lists the latest calls (host, tool, command or path, and how it ended) for 30 days. Output is never kept. |

If the audit log cannot be opened, nothing is served.

The independent service also keeps a full-access warning visible. Restart it
through the client after changing access: a running child retains the level it
started with. HTTP changes apply immediately to new calls.

### Independent-service file tools

These additions apply only to `mcp-serve`, not HTTP MCP, `mcp-bridge`, or the
in-app assistant. Replies retain text `content` and add machine-readable
`structuredContent`.

| Tool | Independent-service behavior |
| --- | --- |
| `terminal_exec` | Separate `stdout`, `stderr`, nullable `exit_code`, `duration_ms`, `truncated`, `timed_out`; optional absolute POSIX `cwd` for this call only. |
| `sftp_list` | Name-sorted `offset`/`limit` pages (default 500, maximum 1000), with `total`, `next_offset`, `has_more`. |
| `sftp_read` | Byte `offset` or `tail: true`, up to 256 KiB per call; returns byte counts, next offset, EOF and truncation. Use `encoding: "base64"` for arbitrary bytes. |
| `sftp_stat` | Size, type, permissions and modification time, without following the final symlink. |
| `sftp_checksum` | Stream a regular file through `sha256` or `sha512` without returning its content. |
| `sftp_upload`, `sftp_download` | Binary-safe file/directory transfers returning task IDs; poll for completion. Offered only with full access and `--transfer-root` (see below). |
| `transfer_status` | Query `transfer_id`, or omit it to list this process's retained history. |
| `transfer_cancel` | Request cancellation; poll until the task settles. |

Command output retains the existing combined size bound. Nonzero exit codes are
results; transport errors, cancellation and timeouts return errors with a null
exit code when unavailable, never an invented zero. `cwd` requires a POSIX remote
shell and a failed directory change prevents the command from running.
`terminal_exec_many` retains its original text contract.

Directory pages are live, not snapshots; restart pagination when the directory
changes. SCP listings and metadata may be approximate (`approximate`). File reads
and checksums reject final-component symlinks. UTF-8 reads replace invalid byte
sequences; base64 preserves bytes, and offsets always count source bytes.
Do not combine tail with a nonzero offset. Checksumming rejects observed size or
modification-time changes, but does not promise an atomic snapshot of a live file.

### Authorizing local transfer directories

Remote full access does **not** automatically grant access to this computer's
files. Confirm **Allow all** for the independent service, then explicitly add
one or more `--transfer-root` arguments to its MCP client configuration and restart:

```sh
motty mcp-serve --data-dir /path/to/motty-data --transfer-root /path/to/transfers
```

Windows argument-array example (keep your client's existing executable and config
structure):

```json
["mcp-serve", "--data-dir", "C:\\Users\\your-name\\AppData\\Roaming\\motty", "--transfer-root", "E:\\Transfers"]
```

Roots must be existing absolute directories. The option is repeatable; without it
upload/download/cancel tools are absent. `local_path` is the full path on the
computer running the MCP server, not the remote host or a cloud client's disk.
Paths outside these roots and local symlink components are refused. Use dedicated
directories you control: do not let untrusted processes replace their directories
or links during a transfer. This restriction is not an OS filesystem sandbox.

Example upload arguments:

```json
{"session":"<host ID from list_sessions>","local_path":"E:\\Transfers\\archive.zip","remote_path":"/tmp/archive.zip","existing":"fail"}
```

Directories require `recursive: true`; paths name the complete destination, not
just its parent. `existing` defaults to `fail`; replacement requires `replace`.
SFTP also supports `resume`. The host's saved protocol choice controls SFTP/SCP;
automatic mode falls back only when the SFTP subsystem is unavailable. SCP resume
is explicitly rejected, never silently restarted.

States are `queued`, `connecting`, `running`, `canceling`, `completed`, `failed`,
and `canceled`. **Only `completed` means success**, not receiving an ID or reaching
100% byte progress. Each MCP process runs at most four transfers and retains 32
records; IDs are not reused across processes. Each task owns its connection, so
canceling it does not interrupt other commands or transfers. Exiting the service
cancels tasks and discards history. Cancellation never undoes committed files;
interrupted SCP uploads can leave partial targets and SFTP partials may remain for
retry. Queueing and completion are audited without file contents; if the initial
audit cannot be written the transfer is not started.

This implements the file/task and single-command portions of issue #133. Separate
sudo authorization, host/group edits, snippets and notes management are not yet
offered; the authorized-host boundary is unchanged.
